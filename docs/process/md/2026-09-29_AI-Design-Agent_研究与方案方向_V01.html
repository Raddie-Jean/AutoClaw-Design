AI Native 产品 Design Agent：研究与方案方向 V01

研究日期：2026-09-29。定位：测试题的研究与路线稿，供后续工作区界面、开放题 Feature 和完整交付包设计使用。产品事实来自公开官方页面；「机会」「方案」「优先级」均为本报告的设计判断，尚未经过真实设计师访谈或 AutoClaw 客户端实测。

01｜先把题目定义清楚

题目包含两项彼此关联、但交付重点不同的工作。

题目 需要回答的问题 建议交付
Task 1：Design 工作区 一次生成结束后，设计师从哪里找到结果，如何预览不同页面与设备、定位问题、继续编辑、管理版本，并交给别人？ 一条完整的“任务完成 → 查看 → 修改 → 评审 → 交付”路径；工作区信息架构、关键状态与核心页面。
Task 2：一个新 Feature 现有生成、预览、局部修改之外，哪个能力最值得加？它解决什么具体阻塞？ 一个问题、一个核心机制、一条端到端路径、价值与验证方法。

题目图片给出的限制是：输入可以是自然语言、截图、Figma、PRD、代码；当前产物格式是 HTML。因而本方案把 HTML/CSS/JS 与所需资源视为可运行的主产物，把 Figma、PNG、PDF 等视为面向不同用途的派生产物。所谓“可直接交付”，至少要说明交给谁、用于什么、哪些内容可以继续编辑、哪些内容已经校验。单纯导出文件不能证明它已达到研发交付质量。

一个重要的现状修正

AutoClaw 官方 2026-08-14 的 Auto Design 介绍已经列出：左对话右画布、需求澄清卡、聊天改大方向、评论改局部、画布微调、桌面/平板/手机/PPT 预览，以及 ZIP、HTML、Markdown、PDF、PNG、PPTX 导出。[S1] 因而 Task 1 的机会不宜写成“从零新增预览、编辑和导出”。本报告将其界定为：把已存在的操作组织成以项目和产物为中心、可以反复返回并安全交付的工作区体验。这只是基于公开资料的判断；真实客户端的信息架构、权限和版本能力仍待验证。

02｜竞品与相邻产品扫描

筛选原则：优先选设计师从“输入材料 → 生成 → 迭代 → 可编辑产物 → 协作/交付”中会遇到的产品；只记录官方页面明确说明的功能。表中“启发”是推论，不能当作该产品的实际效果评测。

产品 / 类型 官方可确认的相关能力 对题目的启发 来源
AutoClaw Auto Design / 综合 Agent 需求澄清、设计生成、对话/评论/画布微调、多视图预览、多格式导出 机会在跨任务的产物秩序、版本语义与交付质量 [S1]
Figma Make / 设计到代码 Figma frame 作为输入；交互原型、点选提示、属性面板、代码编辑；预览复制为可编辑图层；新代码工作流支持分支和提交（部分为 beta） “运行中的设计”与“可编辑设计图层”需要清楚的转换关系和状态 [S2][S3][S4]
Figma Design Agent / 原生画布 在 Figma 画布生成可编辑设计层，覆盖流程、状态、文案和结构 原生图层编辑是一种不同于 HTML 编辑的目标产物 [S5]
FigJam AI / 前期协作 生成板与图、归纳便签、为团队讨论形成结构 Design 模块也应保留需求与决策的上下文 [S6]
Google Stitch / AI UI 文本/图像输入生成 UI 与前端代码，聊天和主题迭代，可粘贴到 Figma；新版支持语音、设计文件与代码库输入 输入材料是持续可追溯的上下文，不只是首次上传 [S7][S8]
v0 / 代码式设计 Figma 截图和 token 输入；在运行预览中选元素改属性或自然语言改结构；应用后形成可对比版本 局部编辑应有“待应用 → 对比 → 新版本”的明确状态 [S9][S10]
Lovable / AI 应用构建 运行界面中点选、可视化修改并保存；历史版本/书签 设计师需要快速修改，也需要能找回认可过的节点 [S11][S12]
Bolt / AI 应用构建 项目中途导入指定 Figma frame；点选并批量提交视觉修改 原设计更新后，应支持带上下文的增量修改 [S13][S14]
Framer / 可视化建站 AI 生成响应式网站，生成后在画布逐层编辑并发布 生成结果必须保留日常设计师熟悉的精细控制 [S15]
Webflow AI / 可视化建站 生成多页站点，在预览画布增删、调整区块，进入编辑器继续工作 页面结构和最终运行结果可以共用一套工作空间 [S16]
Relume / 网站规划 从 brief 到 sitemap、wireframe、style guide，并导出 Figma/Webflow AI 应区分早期结构、视觉方案和后期交付的成熟度 [S17]
Uizard / 快速原型 提示词生成多屏、截图提取风格、手绘线框转数字原型 非 Figma 输入也应被识别为不同置信度的参考 [S18][S19]
Canva Code / 可编辑内容 提示词/模板/HTML 导入互动内容，在 Canva 画布或对话中调整 “外部生成 HTML → 可编辑设计”是用户需求，但转换仍需明确质量边界 [S20]
Anima / 设计到代码 Figma 设计转 HTML、React 等代码，考虑设计系统 开发交付要包括技术框架与组件对应关系 [S21]
Builder Visual Copilot / 设计到开发 Figma 与现有代码组件映射，使用真实设计系统和业务上下文生成界面 从 demo 到可落地，关键在现有组件/代码/数据上下文 [S22][S23]
UXPin Merge / 代码组件设计 用真实代码组件制作原型，支持设计与开发共享组件语义 “可交付”更依赖组件一致性，而不是像素相似 [S24]
Adobe Firefly / 视觉素材 多模型素材生成、生成填充、可编辑模板/矢量，并进入 Creative Cloud 工具继续处理 视觉素材、UI 页面与代码应作为不同产物类型管理 [S25]

从产品抽取的功能地图

这是能力清单，不代表每个产品都具备全部能力。

  1. 输入与理解：文本 brief、PRD 解析、截图参考、手绘线框、Figma frame、设计规范、代码仓库、组件库、品牌素材、网页参考、目标平台与交付格式澄清。
  2. 生成与探索：站点地图、用户流程、低保真线框、多屏 UI、多个视觉方向、文案、图片、图标、响应式布局、交互原型、真实数据演示、前端代码。
  3. 预览与判断：页面/状态切换、桌面/平板/手机预览、交互点击、动效、实际内容填充、并排比较、版本差异、异常/空/加载状态、分享评审。
  4. 修改与控制：全局对话、选区提示、评论锚点、属性面板、直接改文字、拖拽/重排、token 替换、设计系统约束、代码编辑、撤销恢复、批量应用修改。
  5. 协作与组织：项目/任务、设计集、页面、方向、版本、分支、固定里程碑、评论、责任人、权限、来源追踪、决策记录、状态标记。
  6. 导出与交付：HTML/ZIP/React、Figma 可编辑图层、PNG/PDF/PPTX、共享预览链接、资源包、交互说明、组件映射、设计 token、版本说明、验收清单。

竞品结论

  • 生成已经不是唯一差异点。 Figma、v0、Lovable、Bolt 和 Canva 都提供生成后的局部可视化修改；仅把聊天框移到画布旁边难以构成新价值。[S2][S9][S11][S14][S20]
  • 设计文件与运行代码正在相互靠近，但不能假设无损双向转换。 Figma Make 可将预览带回可编辑图层，Canva Code 可导入 HTML；这证明方向有需求，并不证明任意 HTML 能完整恢复为高质量 Figma 组件、约束和交互。[S3][S20]
  • 版本与差异是 Agent 工作的安全栏。 v0 将视觉修改应用为新版本，Bolt 允许中途增量导入，Figma 新代码流程连接分支/提交。对设计师而言，关键问题是“我改的是哪一个方案、哪些地方变了、能否撤回”。[S4][S9][S13]
  • 高质量交付依赖项目上下文。 Anima 和 Builder 都强调设计系统、组件或代码上下文；这支持把“格式导出”与“达到可落地质量”分开。[S21][S22]

03｜AI 能力与边界：按产物而非按模型划线

产物 / 工作 AI 适合承担 边界与设计师必须判断的部分 工作区应显示什么
需求摘要、任务卡 从 PRD/对话提取目标、平台、页面、约束、缺项 需求含糊、优先级冲突、商业取舍 输入来源与未确认假设
用户流程、信息架构 给出候选流程、页面清单、内容层级 是否符合真实用户行为、组织流程和产品策略 候选方案与决策理由
视觉方向、界面初稿 快速生成多方向和响应式初版 品牌判断、识别度、复杂内容可读性 方向、版本、对比入口
交互原型与 HTML 补充点击路径、动效和可运行预览 真实业务逻辑、数据权限、极端状态、性能 真实/模拟数据标识、未覆盖状态
局部修改 按选区/批注改文案、样式、结构 非预期波及、组件与全局 token 破坏 修改范围、前后差异、回退点
Figma 可编辑层 从 HTML/截图抽取层级与样式，生成可修订设计稿 语义组件、Auto Layout、变量、交互常有损失；不应保证 1:1 转换完成度、需手工修正项
开发交付包 汇总源文件、资源、token、交互和状态说明 架构、可维护性、安全、可访问性与生产代码仍需研发审查 清单、检查结果、责任人和版本

建议用三级能力声明：自动可完成（如生成缩略图）、AI 提议后人工确认（如替换全局组件）、仅提供辅助证据（如“是否真正满足用户需求”）。页面中避免统一写“已完成”掩盖这三种差异。

04｜传统设计与 AI 辅助设计的模式变化

阶段 传统设计的典型动作 AI 辅助后的变化 新风险
理解任务 读 PRD、开会、整理素材 Agent 先提炼需求并列出缺项 假设被误当作确定需求
探索方向 手动线框与视觉发散 同时生成多个可运行方向 方案多而决策依据弱
深化设计 画布逐层编辑并做原型 选区提示、属性修改与直接编辑并存 AI 大范围改动覆盖细节
评审迭代 截图、标注、会议与文件复制 评论与改动可以挂到同一产物版本 评论指向的版本失效
交付研发 Figma 标注、资源导出、口头说明 HTML/代码、可编辑稿和规范可并行输出 多份产物不一致、质量未验证

因此，工作区不应按“聊天记录”组织设计工作。更适合的基础对象是：项目 → 设计任务 → 设计集 → 方向 → 版本 → 页面/状态 → 交付快照。同一版本下的 HTML、预览图与其他导出物要能互相追溯。

05｜推荐的 Task 1：Design 工作区

核心用户与场景

主用户是负责继续完善并交付界面的产品设计师。选一个足够典型、能展示整条链路的场景：设计师收到“在现有 SaaS 控制台中新增成员邀请流程”的 PRD，同时提供旧版 Figma 页面、品牌 token 和当前代码。Agent 生成桌面与移动端的可运行 HTML 初版。设计师需要检查信息层级、邀请码错误态、移动端布局，修改后交给产品经理评审与前端研发。

工作区对象与结构

项目「团队管理」
└─ 任务「新增成员邀请」〔进行中 / 待评审 / 可交付〕
   ├─ 输入：PRD、旧 Figma、设计系统、代码引用
   ├─ 设计集：邀请流程
   │  ├─ 方向 A / 方向 B
   │  └─ 版本 v1 → v2 → v3〔已确认〕
   │     ├─ 页面：邀请入口、填写邮箱、成功/错误
   │     ├─ 设备：桌面、移动
   │     └─ 主产物：HTML 项目 + 资源 + 版本元数据
   └─ 交付快照：预览链接、ZIP、设计说明、检查记录

工作区建议采用稳定的三栏：左侧是任务与产物树（找得到）、中央是可交互预览与对比（看得清）、右侧是随所选对象变化的对话/属性/评论/核验（改得准）。顶部固定项目面包屑、当前方向与版本、状态以及“生成交付快照”。首页提供任务卡与最近产物，进入任务后默认定位到最新确认版本，而非任意一次聊天输出。

关键路径与屏幕状态

  1. 完成生成：任务卡从运行中变为“待检查”，展示页面数、方向数、主产物类型与未确认假设。进入工作区自动打开第一个可运行预览。
  2. 浏览结果：左侧树按流程和页面组织；中央切设备和交互状态；设计师能在方向 A/B 与 v1/v2 间并排或叠加比较，并看到每次变更摘要。
  3. 定位并修改：选择具体元素或区域；小改动走属性/文字，结构改动走带选区的 Agent 指令；修改先形成预览草案，再由设计师应用为新版本。操作前后可对比，支持撤回。
  4. 评审协作：PM 在“v3/移动端/错误态”的具体位置留言；设计师接受、回应或转为待办。评论与版本绑定，旧版评论不会漂移到新版页面。
  5. 检查并交付：选择接收对象（PM 评审 / 设计团队继续编辑 / 研发实现）；系统给出不同交付内容与限制，固定一个不会被后续修改覆盖的交付快照。
旅程阶段 用户此刻想确认 传统/当前可能断点 工作区的关键响应
接收初稿 “生成了什么，能否直接打开？” 结果散落在聊天附件或文件夹 任务卡汇总页面、设备、方向与失败项；一键进入可运行预览
探索判断 “哪个方向更符合需求？” 多个 HTML/截图缺少共同尺度 同一页面并排对比，保留需求与设计系统引用
精修迭代 “改这一处会影响哪里？” 反复提示容易改乱其他区域 选区修改、影响范围、草案预览、新版本及回退
团队评审 “评论对应的到底是哪一版？” 截图与评论脱节、旧意见漂移 绑定页面/状态/版本的锚点与处理状态
交付接力 “对方能继续做什么，还缺什么？” 多个导出文件不一致，口头补充多 按接收对象生成固定快照、可编辑度与待办清单

核心异常状态必须设计：生成失败但保留已完成页面、预览依赖缺失、引用的 Figma/代码已更新、两次修改冲突、导出失败、HTML→可编辑稿有损、评论所在元素在新版被删除。

Task 1 的路径验收标准：一位首次使用的设计师应能在生成结束后找到全部页面与状态、指出当前确认版本、完成一次局部修改并回退、把指定版本连同未完成项交给 PM 或研发。后续用任务测试记录完成率、用时与误操作，而不是只询问“界面是否喜欢”。

交付格式的真实含义

交付目标 推荐内容 不能省略的说明
让人评审 只读交互预览 + 页面/状态目录 + 评论入口 当前版本、模拟数据与未完成路径
设计师继续编辑 可编辑层文件（若可转换）+ HTML 主产物链接 + token/组件对照 转换损失和仍需手工整理的层
前端接手 完整 HTML/代码 ZIP + 资源 + 页面/状态表 + 组件映射 + 交互说明 运行方法、技术假设、检查结果和未解决问题
汇报归档 PDF/PNG + 决策摘要 静态材料无法承载全部交互

这里不承诺将任意 HTML 一键变成生产级 Figma 文件或生产代码。可编辑层是面向设计继续工作的目标，仍需转换质量评估；代码包也需要研发检视。

06｜推荐的 Task 2：Design Review Agent（交付前设计核验）

为什么选它作为唯一深入的 Feature

候选方向 用户价值 与现有能力的关系 主要代价 / 风险 判断
HTML → Figma 可编辑稿 方便设计团队继续打磨 针对格式断点，但已有市场案例 转换容易丢组件语义、约束与交互；实现质量决定价值 可作为后续能力，当前不承诺无损
多人实时共创画布 强化协作 与现有评论/画布接近 权限、冲突、同步复杂，难在一条测试路径中讲透 暂不作为开放题主轴
交付前设计核验 降低遗漏与返工，直接提升交付可信度 串起已有生成、预览、修改、导出 需要清楚界定自动检查与人工判断 推荐深入

用户问题：设计师已经能很快生成和修改 HTML，但在发给 PM 或研发前，仍要人工逐页检查状态、断点、品牌规范、关键交互与各导出物是否一致。生成速度越快，遗漏越容易扩大。

Auto Design 官网已提到可以在聊天中要求检查信息层级、可读性和易用性。[S1] 本 Feature 增加的是面向拟交付版本的结构化核验、可定位证据、修复前后对比和随快照留存的结论，而非把普通聊天式建议重新命名为设计评审。

唯一核心机制：围绕当前“拟交付版本”生成带证据的核验卡。每张卡指向具体页面/设备/元素，说明“预期依据 → 实际表现 → 风险 → 修复建议”；设计师可定位、让 Agent 在独立草案中修复、对比前后，并明确接受或忽略。核验结论随交付快照冻结。它是审阅与决策机制，不是另做一个生成器。

核验从可机器判断的项目开始：页面和 PRD 要求覆盖、桌面/移动布局溢出、可访问性基础检查、token/组件偏差、图片或字体缺失、链接与交互路径可用性、导出前后的视觉差异。对于“是否符合品牌气质”“流程是否适合目标用户”，Agent 只提出判断依据与待确认问题，不自动给出通过结论。

一条核心体验路径：

设计师点击「准备交付」
→ Agent 读取当前版本、PRD、设计系统与所有页面状态
→ 输出按严重度排序的核验卡，预览中标出位置
→ 设计师选择一张卡，查看证据和建议
→ Agent 在草案版本修复，展示桌面/移动前后对比
→ 设计师接受修复或记录例外
→ 系统生成带“已验证 / 待确认 / 已知问题”的交付快照

为什么值得做：它连接现有的生成、预览、局部修改和多格式导出，将“看起来完成”变成“知道哪些已完成、哪些仍有风险”。新价值是可信的设计交付状态，不是再加一种导出格式。[S1][S9][S22]

验证指标：① 设计师从初稿到首次可评审交付的时间；② 交付后因遗漏页面/状态被退回的比例；③ 核验卡被接受修复或主动忽略的比例；④ 修复造成的回归问题数。先用 5–8 位产品设计师做任务测试，观察其是否能在不解释系统的情况下找到问题、理解证据、完成修复和交付。此处人数是研究计划，不是现有数据。

07｜设计执行步骤与阶段成果

阶段 要解决的决策 可验证产物
1. 基线与用户问题 现有 Auto Design 到底覆盖到哪里？设计师最痛的断点在哪？ 现状能力图、竞品矩阵、访谈问题、优先问题陈述
2. 核心场景与对象模型 谁在什么任务下操作哪些产物？主产物与导出物关系是什么？ 主场景、任务流、产物结构和状态定义
3. Task 1 工作区 如何在一条路径里完成查看、预览、编辑、版本管理和交付？ 信息架构、低保真流程图、关键页面与空/错/加载态
4. Task 2 单点深入 核验 Agent 如何发现、解释、修复并记录问题？ Feature 机制、核心交互、边界与指标
5. 验证与交付 路径是否可用、论证是否成立、设计与说明是否一致？ 原型走查、可用性测试记录、最终方案、过程文档、MD/PDF/源文件包

优先级建议：先用一个“任务完成后继续编辑并交付”的场景把 Task 1 做完整，再让 Task 2 插入“准备交付”节点；不要把 17 款产品的功能全部搬进同一个工作区。最终方案中至少展示任务完成页、设计工作区、局部修改/版本对比、核验卡、交付快照这五个关键画面，并写出它们之间的跳转及失败状态。

08｜本版仍需验证的假设

  • 尚未获得 AutoClaw 客户端访问、设计师访谈或内部产品指标。官网说明不等于真实界面和实际交付质量；后续要以产品实测修正现状图。[S1]
  • 题面称产物是 HTML，官网同时描述多格式导出；需确认 HTML 是唯一的可编辑主数据，还是还存在独立画布文档模型。此事直接影响编辑、版本与 Figma 输出方案。
  • 可编辑 Figma 文件是否为必交目标，需要在完整方案中作为产品策略选择评估：其价值大，但转换保真度与维护成本也高。
  • “可直接交付”需要以 PM 评审、设计接力、研发接手三个接收对象分别定义。若测试题评委只关注其中一个，可在后续方案中收窄。
