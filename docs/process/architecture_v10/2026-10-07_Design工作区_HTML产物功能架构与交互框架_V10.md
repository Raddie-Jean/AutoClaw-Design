# AutoClaw Design 工作区｜HTML 产物功能架构与交互框架 V10

> 2026-10-07 · 基于已有用户旅程、V07 定域修订定义及 V08 原型继续深化的**方案假设**。本稿描述拟设计能力，不代表 AutoClaw 当前已具备这些功能。配套 8 张 SVG 可导入 Figma 继续编辑；`index.html` 供浏览和讨论。

## 1. 本轮要解决的任务

设计师拿到 Agent 生成的 HTML 初稿后，需要在同一个任务里**看全、改准、交清**：看清方向、页面、状态和设备覆盖；对指定文字或界面对象连续微调，不反复重生整页；让 PM 看见可运行的同一版本，让开发拿到可复现的源码、资源和决定记录。

本轮聚焦 **AutoClaw 自生成且源文件可用的 HTML 项目**。HTML/CSS/JS 与实际引用的资源共同构成可运行主产物。PRD、截图、Figma、外部网页等作为输入或参考；PNG/PDF/ZIP 等是从某个版本派生的输出。不同格式能被关联、预览和追溯，不等于能无损互相转换。

核心产品判断：工作区的一级导航按设计师要做的**判断**组织，而非按文件格式或 AI 工具组织。文件栏是上下文面板；“修订”是贯穿预览与候选审阅的操作，不是孤立的聊天记录。

## 2. 痛点 → 产品能力 → 验收信号

| 用户旅程断点 | 当前任务中的具体问题 | MVP 能力 | 应观察的信号 |
|---|---|---|---|
| 看不全 | 初稿含多个页面/状态/设备，设计师只看见一个截图或首页 | 成果清单、覆盖矩阵、可运行预览；标记未生成/预览失败状态 | 不靠询问 Agent，能找出缺失的错误态并打开 Mobile 预览 |
| 改不准 | 用整段提示词重生时，已接受内容可能改变；画圈又未必对应源码对象 | 文字内联修改、DOM 点选、画笔锚点统一进修订卡；生成前确认命中目标、范围和保留项 | 能指认改动目标，并发现候选超出预期的变化 |
| 改不稳 | 全局样式与复用组件让“只改这里”影响其他页面 | 隔离候选、视觉对比、文件变更摘要、受影响状态清单 | 两次连续微调后，先前采纳的改动仍保留 |
| 评不清 | 设计师采纳一次改动与 PM 同意方案被混为一谈 | G1 概念、G2 Demo 的独立评审记录；评论锚定版本与对象 | PM 知道现在看的是哪个方向/版本，能留下未解决意见 |
| 交不清 | 截图、HTML、资源和说明散落，开发难复现评审状态 | 固定版本快照、清单、运行入口、源码包、已知问题；同一版本 ID | 前端可按交付说明复现指定状态，且与评审预览一致 |

以上是设计假设与测试目标，不是已测得的痛点发生率。

## 3. 内容模型：把“文件”变成可追溯的成果关系

### 3.1 五种对象

| 对象 | 包含什么 | 权威与主要操作 |
|---|---|---|
| 参考资料 `Reference` | PRD、截图、Figma 链接、规范、竞品示例 | 原出处为权威。可查看、引用到修订卡、标注来源；不在工作区伪装成可编辑 HTML。 |
| 可运行项目 `Source bundle` | 入口 HTML、CSS、JS、字体/图片等被引用的资源、运行配置 | **HTML 主产物的权威源**。预览、修订和版本都以它为基线；依赖缺失则阻止“可交付”标记。 |
| 设计资产 `Asset` | 图标、插画、图片、字体、组件相关资源 | 区分已引用/未引用、原始/生成、许可证或来源；替换资源须检查引用位置。 |
| 修订候选 `Candidate` | 基线版本、目标、意图、改动文件、预览与检查结果 | 隔离于工作版。可继续限定、采纳或放弃；不能直接冒充正式版本。 |
| 交付快照 `Snapshot` | 固定的版本 ID、源码与依赖、页面状态清单、评审结论、运行说明、问题单 | 冻结、可复现；导出的 ZIP/PDF/截图记录 `derived_from_version`，不反向覆盖源。 |

### 3.2 必须保留的关系

`项目 → 任务 → Design 工作区 → 方向 → 版本 → 页面 × 状态 × 断点 → 对象`。每个文件至少显示名称、格式、来源、归属方向/版本、用途、更新时间、被引用情况。每条候选记录 `base_version`、`target_ref`、`changed_files`、`affected_views` 与决定。导出物必须记录 `derived_from_version`；否则它只是未认证的附件。

文件栏默认**按用途**分组：`主稿与运行资源 / 参考资料 / 候选与版本 / 派生导出`。可按格式筛选，但不把格式做成一级导航。选择一个文件时显示“用于哪些页面/状态、由哪个版本产生、能做什么”。例如点开 PNG，若它是预览截图，主操作是“回到生成它的可运行视图”，而不是在 PNG 上假装可修改 DOM。

外部 HTML 若无源代码、路由和资源依赖可控性，仅作为参考网页或导入待检查项；**MVP 不承诺任意网址原位编辑**。Figma 文件可作设计输入或外链，但不承诺与 HTML 双向无损同步。

## 4. 功能架构与信息架构

### 4.1 一级结构

```text
AutoClaw 左侧：项目 / 任务
  └─ Design 任务：邀请成员流程
      ├─ 成果总览        方向、页面/状态覆盖、待处理项、最近版本
      ├─ 预览与编辑      可运行视图 + 方向/页面/状态/设备/版本上下文
      │   ├─ 选中文字 / 点选元素 / 画笔圈选
      │   └─ 右侧：修订卡 / 文件与引用 / 评论
      ├─ 修订审阅        待审候选、视觉差异、源文件与影响范围、决定
      ├─ 版本与评审      工作版轨迹、G1 概念、G2 Demo、意见与决定
      └─ 交付            固定 G3 快照、复现入口、文件清单与导出
```

**始终可见的定位栏**：`方向 B / 邀请成员 / 邮箱错误态 / Mobile 390 / 工作版 v4`。用户从文件、评论或候选跳转时，这组上下文同步变化，避免在错误状态上改稿。

**精准调优有两条路径**：当文案或样式属性能稳定映射到 HTML/CSS 时，设计师可直接改确定值（例如文案、间距、字号、颜色 Token），即时查看当前状态并撤销；右侧标出实际写入的文件与共享范围。当目标是布局关系、层级或交互规则时，用自然语言描述意图和“保持不变”项，先生成隔离候选。画笔只负责指出视觉区域，不能绕过命中确认。这样常规微调不必每次重新提示生成，复杂变更也不会直接覆盖工作版。

**信息架构与权限**：设计师可创建/采纳修订；PM 可评论并对 G1/G2 给出确认或待修改结论；前端可在 G2 前对技术难点预检，G3 后接手。MVP 可以用角色标签和审阅记录模拟，不依赖多人实时协作。评审结论必须指向固定版本，后续修改使其进入“需复核”而非静默保留已通过状态。

### 4.2 功能模块与优先级

| 模块 | P0 必须具备 | P1 再扩展 |
|---|---|---|
| 成果索引 | 扫描入口与页面/状态/断点；失败/缺失显式呈现 | 1–3 方向并排、AI 自动补全覆盖建议 |
| 可运行预览 | 同源 HTML 预览、设备切换、状态入口、固定版本标签 | 更丰富的交互录制、场景回放 |
| 定域编辑 | 确定文字、有限的映射属性微调、DOM 点选的 AI 修改、受限画笔；命中对象和范围确认；保留项 | 批量跨视图修订、自然语言复杂约束模板 |
| 候选审阅 | 基线/候选对比、变更文件、受影响视图、采纳/放弃 | 自动视觉回归与更细粒度的风险解释 |
| 文件与版本 | 用途分组、引用关系、工作版与候选区分、版本回退 | 多人并行分支、外部仓库同步 |
| 阶段评审 | G1/G2 的结论与关联版本；前端技术预检项 | 异步对象评论与通知 |
| 交付 | 冻结 G3 版本、可运行入口、源码/资源 ZIP、状态与问题清单 | 映射设计系统、自动接入生产仓库 |

MVP 的最小闭环是：**找到目标状态 → 局部修改 → 审阅影响 → 采纳工作版 → PM 确认 Demo → 固定版本交付**。无限画布适用于前期发散，不是本轮 HTML 精修的主编辑面。独立图像/视频生成器、无损格式互转、生产仓库自动合并都不纳入。

## 5. 一条主链路及分歧处理

示例任务：`方向 B / 邀请成员 / 邮箱错误态 / Mobile 390 / v3`。设计师认为错误提示距输入框太远，但 Desktop 与成功态要保持不变。

1. **成果总览**：进入方向 B，看见“邀请成员”页面、错误态、Mobile 与 Desktop 的覆盖；点击 Mobile 错误态。未生成的状态标空位，预览失败标错误，不使用旧截图填充。
2. **聚焦预览**：选中错误提示元素。右侧修订卡自动带入目标、页面、状态、设备与基线 v3；用户写“移到邮箱输入框下方”，保留“桌面端、成功态、品牌样式”。
3. **生成前确认**：系统高亮实际命中的 DOM 对象，并显示共享样式可能影响的视图。画笔若命中多个对象，用户先选目标；不能可靠命中时降级成“页面级修改建议”，不能继续标称精准修改。
4. **隔离候选**：生成 `v3-c1`，保持 v3 不变。候选展示可运行预览、修改的源文件、可能受影响的视图及失败检查。用户可继续限定，产生下一候选，而不是覆盖前一个。
5. **审阅决定**：比较 Mobile 错误态原版/候选，并抽查 Desktop、成功态。确认后采纳为工作版 v4；若越界则调整或放弃。**采纳不等于 PM 已批准。**
6. **G1/G2 评审**：草图概念确定时 PM+设计师确认方向 G1；Demo 阶段评审可运行流程、响应式、异常态，前端对风险点做预检 G2。若评审后更改 v4，批准状态需要复核。
7. **G3 交付**：以经过评审的版本创建快照，下载源码/资源包及状态清单、运行说明、决定与已知问题。必须满足 `preview.version_id = snapshot.version_id = export.derived_from_version`。

**确定文字或稳定映射的局部样式属性**可以直接写入可撤销的工作草稿，并记录版本差异；若属性来自共享 Token、会影响其他实例，或涉及 AI 生成、结构、复杂样式，则先走隔离候选。用户依旧可以在工作草稿上继续生成候选，基线自动更新。

- `05_预览与定域编辑线框.svg`：可运行 HTML 居中；顶栏固定上下文；右侧修订卡在确定值微调与 AI 指令之间切换，展示命中对象、范围、意图和保留项。文件抽屉能查看源文件与参考。
- `06_候选审阅线框.svg`：并排预览为主，变更文件与受影响视图紧邻决定按钮；失败检查必须可见。

## 7. 需要验证的关键风险

1. **页面与状态索引的真实性**：HTML Demo 可能没有显式路由或状态入口。无法自动枚举时允许设计师补录状态与进入方式，未验证状态不能算已覆盖。
2. **目标到源码的映射**：DOM 标识不稳定、生成代码重复、画笔只提供截图坐标。必须在生成前显示命中对象；基线变更后目标失效就要求重定位。
3. **“精准”对共享样式的限制**：改 CSS 可能影响多个页面，候选审阅应揭示影响范围。源文件 diff 与截图差异都不能单独证明交互逻辑正确。
4. **可交付的边界**：ZIP 是可复现的设计规格/工程起点，不自动成为生产代码；前端仍需核对路由、真实数据、接口、权限、性能与无障碍。

建议下一轮用一份真实 Agent 生成的 HTML 测试任务校验：能否识别 3 个关键状态、连续完成两次局部修改、发现越界变化，以及由前端独立复现 G3 指定状态。若这些做不到，应先修基础索引/版本能力，再扩展协作或无限画布。
