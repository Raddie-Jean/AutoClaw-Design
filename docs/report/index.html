AutoClaw Design Agent｜完整文稿汇总

本稿整合测试题、AutoClaw 界面截图、设计过程文件、双任务原型，以及新增的竞品调研、MVP 过程和 PRD 材料。它说明当前方案如何形成、具体解决什么问题、原型验证到了哪里。本稿是方案汇总，不将另一份探索 PRD 的设想视为已上线能力，也不把可点击 Demo 视为用户测试或工程可行性验证。

01｜题目、对象与方案范围

测试题的主产物是 HTML：用户可用自然语言、截图、Figma、PRD 和代码等材料，让 Design Agent 从零生成网页或 UI，也可以基于已有设计继续修改。Task 1 要求在一次任务结束后，让用户能够查看结果、运行预览、继续编辑，并管理同一任务产生的多个文件。Task 2 要求选择一个最值得增加的 Design Feature，深入说明用户问题、机制、交互与价值。

本轮以产品设计师为主要用户，选择“Agent 已生成初版，设计师要局部修订并交给开发”作为 Task 1 的核心场景。Task 2 选择版本锚定的协作建议：PM 或前端对指定版本、页面状态和对象提出建议，设计师决定是否转成修改候选。两题在同一产品结构下衔接，但 Task 1 不依赖多人参与才能成立。

交付标准不是“生成了一张看起来正确的截图”，而是设计师能确认当前主稿、知道修改影响了什么、保留原版本，并让预览与最终文件指向同一版本。当前原型用 SVG 示例具体演示这一链路；它尚未验证任意 HTML/CSS/JS 项目的对象定位和源码回写。

03｜设计工作路径与待解决问题

设计师的工作不是在第一次生成时结束。需求定义之后，团队需要比较方向、确定概念、检查运行体验，再把可交付版本交给研发。AI 缩短了初版制作时间，却同时引入了“哪个文件是主稿”“某次提示是否重做了整页”“评审的是哪版”这些需要在产品界面中明确回答的问题。本项目尚无用户频率数据，以下按任务链路整理为设计假设，不是统计结论。

阶段 设计师需要判断 当前风险 对应机制
需求输入与方向形成 目标、参考与约束是否明确 模糊指令被直接执行，后续返工 Agent 在关键歧义处追问，保留输入材料与确认记录
初版生成 哪个是可运行主稿，哪些是截图或参考 多个格式混在消息里，主从关系不清 任务结果卡进入产物工作区；主稿、资源、参考、派生物分组
预览与局部修订 改哪里、保留什么、会影响哪些状态 重写提示词导致非目标区域变化 运行预览定位对象；确定值直接调整，结构变化生成隔离候选
方案评审 PM、前端看到的是哪一版、哪种状态 反馈脱离版本和对象 建议锚定版本、页面／状态、对象，设计师决定是否采纳
定稿与交付 预览、文件和说明是否一致 “Agent 完成”被误认作“人工批准” 人工确认交付快照；文件清单与可机械检查项随版本保存

PM 与设计师在方向收敛后、进入完整 Demo 前共同确认概念，可降低后续整案返工的风险；前端可在结构和技术约束需要提前判断时参与。这里是建议的评审时点，并未经过实际团队任务测试。Task 2 原型先验证“反馈被锚定且不能直接覆盖工作版”，不声称已实现完整在线评审流程。

04｜研究观察与方案演进

用户提供的 Lovart 录屏截帧显示对象选中、上下文工具、Quick Edit 与新旧结果并置；万相截图显示左侧指令过程与右侧多节点画布；WorkBuddy 截图显示项目／任务列表、对话文件卡和右侧画布。它们分别提示三种可借鉴的组织方式：围绕对象下达局部意图、在空间上比较多种结果、让任务记录与产物并列。但这些画面不能证明 HTML DOM 能被准确圈选并回写，也不能证明多人共同编辑的可靠性。

新增竞品材料提出 Figma、Stitch、Framer、Pencil 等工具的不同路线，可作为后续核查清单。由于其多数能力说明和数字未附逐条原始证据，本轮不据此宣称“市场空白”或“行业共识”。本项目更可靠的决策依据，是测试题对 HTML 的明确要求、AutoClaw 已有界面、用户提供的可见竞品画面，以及本地原型走查发现的问题。

方案从“无限画布承接所有格式”收敛为“可运行主稿 + 关联资料 + 轻量画板”。原因是题目要求处理 HTML：画板适合摆放参考、截图和方案卡片，真实的页面交互仍需要运行预览。早期独立 Design App 结构也被收回到 AutoClaw 任务内：左侧保留项目与任务，中间保留 Agent 对话，右侧随任务结果打开产物工作区。最后将生成后的单人产物链路与未来协作 Feature 拆成两个独立任务，避免 Task 1 被邀请流程稀释。

AI 在过程中承担资料归类、信息结构草拟、HTML/SVG 状态稿生成和可点击样例制作；设计师明确题目边界、纠正产品结构、选择核心功能，并对原型与文稿的表述作最终判断。可核对的过程文件包括研究方向、MVP 初稿和信息架构。

05｜四项关键产品决策

决策 当前方案 取舍与尚待验证的问题
入口沿用 AutoClaw 任务 Agent 完成消息中的产物卡打开右侧工作区 新增材料建议把产物库固定左栏；当前以真实任务入口和 当前原型为先，不引入平行的 Design App
源文件是权威主稿 HTML、CSS、JS 与依赖资源构成运行主稿；截图和 PDF 为派生或参考 当前原型的实际修改对象是 SVG 样例，HTML 同源编辑需要单独验证
局部修改先成候选 对象定位、修改意图、影响范围、候选对比与人工采纳形成闭环 画笔圈选坐标到 DOM／组件的映射、共享样式影响仍未知
把“完成”与“确认”分开 Agent 执行状态、设计候选状态和交付快照分别记录 新增 PRD 的四态模型可借鉴，但本轮不把 draft/candidate/approved/superseded 全套定义为已验证需求

在数据语义上，Agent 已完成生成 只表示执行结束；设计师已采纳候选 表示工作版更新；已确认交付 表示某一版本的文件和说明被固定。三者不能共用一个 “done”。新增资料提出保留 manifest、不可静默覆盖历史、人工审批和确定性门禁；当前原型已演示版本保留、人工定稿和 SVG 文件结构检查。真实 HTML 项目还需定义具体文件校验和失败处理。

06｜信息架构与界面载体

AutoClaw
├─ 左侧：项目 / 任务
├─ 中间：Design 任务对话、输入材料、执行记录、完成结果卡
└─ 右侧：当前任务的产物工作区
   ├─ 成果：主稿、资源、参考、派生物、轻量画板
   ├─ 预览与编辑：页面 × 状态 × 设备 × 版本、对象定位、修改意图
   └─ 版本与交付：工作版、隔离候选、差异、采纳记录、交付快照

内容关系为 Design 任务 → 产物集 → 主稿／参考／派生文件 → 视图 → 对象 → 候选 → 工作版 → 交付快照。视图至少需要记录页面、状态、设备和版本。参考文件不得被 Agent 悄悄改写；派生截图应记录来源版本。可运行预览与下载源文件必须来自同一工作版，否则“看见的”与“交给开发的”会分离。

轻量画板仅用于摆放与比较产物卡；点击 HTML 主稿进入聚焦运行预览，不把静态卡片当成网页编辑器。右侧空间有限时，以“成果／预览编辑／版本交付”三个工作态切换，而不是在同屏堆满文件树、画布、参数面板和聊天。对象选中时，画面高亮、对象名称和编辑控件应对应同一目标；若圈选不能解析到稳定对象，应先让用户确认命中范围。

07｜Task 1：从初版到交付的核心链路

任务完成与识别。 Agent 在对话中给出完成结果卡，展示主稿入口、文件数量、未处理问题。设计师打开右侧成果页，区分 HTML 主稿、运行资源、截图、PRD 和 Figma 引用。缺失依赖的主稿可查看文件，但不得标记为“可运行交付”。

聚焦预览与修改。 设计师选择 页面／状态／设备／版本 后运行预览，点选对象或用画笔圈选。确定性属性可输入明确值；可能改变结构的自然语言指令先生成隔离候选，并记录“保留哪些区域”。候选与原工作版并排审阅，显示目标对象、改动范围和需要复核的视图。设计师采纳后生成新的工作版，旧版保留可追溯。

固定交付。 设计师确认版本后，系统保存不可静默覆盖的交付快照，包含源文件、依赖、运行入口、预览来源版本、检查结果和已知问题。能机械判断的缺失文件、不可解析结构等自动检查；素材授权、业务验收和最终采用由人判断。新增 PRD 中“定稿等于复制”的建议适合作为实现方式，但最终的复制／快照策略仍需结合 AutoClaw 存储模型确认。

测试 1 原型用一个可核对的 SVG 示例走完链路：确认 1512×945 画板和矢量／文字要求；生成首版；选择输入卡片，把圆角从 25px 改为 12px；比较并采纳 v2；固定版本；检查实际 SVG 尺寸、文字与位图元素，再下载 SVG 和 manifest。自然语言理解与生成进度是本地模拟，属性修改与文件结构检查可在原型内操作。它证明样例流程可走通，不证明 HTML 项目的任意局部编辑已实现。

08｜Task 2：版本锚定的协作建议

当 PM 或前端说“这个按钮需要改”，设计师需要知道对方查看的是哪个版本、哪个页面状态和哪个对象。Task 2 的最小机制是把建议绑定 version_id + view_id + target_ref：受邀者看到固定位置的预览并提出意见，建议不直接覆盖工作版；设计师将其转成候选，比较后采纳或保留原方案。版本变化时，旧建议仍留在原版本，新的决定另行记录。

测试 2 原型从已有首页 v1 进入独立评审任务，演示建议、候选、采纳和本地评审记录下载。邀请与反馈不接入外部服务，刷新会重置。多角色权限、在线同步和研发真实技术评审尚未验证，不能以可点击页面代替其工程设计。

09｜设计稿还原、规范与产出过程

设计稿先还原用户提供的 AutoClaw 基础界面，再扩展 Design 工作区。现有 统一界面与可视化设计规范记录了布局、色彩、字体、图标、组件和交付规则；1512×945 画板与 280 侧栏／420 对话／812 工作区是本项目的执行基线，不冒称 AutoClaw 官方精确值。

设计稿的结构变化有三步：基础界面与图标还原；根据“套壳、不符合 Agent 操作流程”的反馈，把产物入口接回任务结果；将 Task 1 的生成—修订—交付和 Task 2 的协作建议拆为独立可演示链路。测试 1 文件包含 14 张关键状态 SVG、独立 HTML、预览和实际下载的交付样例；测试 2 文件包含 4 张评审状态 SVG 与独立原型。Figma 导入辅助工具已做语法与输入检查，尚未在 Figma 实测组件和文字保真度。

10｜MVP 范围、验证与下一步

本轮优先保留任务入口、产物角色识别、主稿运行预览、单对象局部修改、隔离候选、版本采纳和同版交付检查。后续探索包括画笔到 DOM 的稳定映射、跨页面和响应式影响分析、设计 token 的语义约束、跨产物规范继承、多角色权限及在线同步。无限画布绘制、全功能 Figma 式拖拽和多人实时同编不进入当前 Task 1 MVP；轻量画板仍保留用于比较与组织。

已完成的是本地原型走查、SVG 样例的实际属性修改与导出结构检查，以及报告中 20 页画板、文稿和双任务入口的浏览器检查。尚无真实设计师可用性测试数据，也没有用真实 AutoClaw Agent 输出的 HTML 项目验证连续修改。下一轮应选一份真实生成的 HTML/CSS/JS 产物，让设计师完成“找到主稿—运行预览—两次局部修订—比较影响—交给开发”的任务；同时检查 DOM 定位准确率、未选中区域是否变化、预览与导出文件是否同版，以及失败时能否回退。PM 和前端再分别检查固定版本的建议是否清楚、交付包能否复现。

本报告的汇报画板负责展示方案要点，交互演示负责操作两条原型路径；本完整文稿保留资料来源、方案取舍和验证边界。原探索稿与当前方案的差异已整理为PRD 修订稿。打开浏览器时请使用 index.html#document，index.template.html 是生成用源文件。
