AutoClaw Design Workspace PRD｜修订 V0.4

2026-10-12 · 方案评审稿。以测试题与现有 V13 双任务原型为当前方案基线。本文件修订另一智能体的 探索 PRD v0.3，保留原版供追溯。这里的 P0/P1 表示建议优先级，不表示已经过用户或工程验证。

1. 本次修订的依据与变化

测试题 Task 1 的主产物是 HTML，要求完成一次 Design 任务后自然地查看、预览、编辑并管理相关文件；Task 2 是选择一个新的设计能力深入。原探索稿提出的状态留痕、局部编辑和交付检查有价值，但把“已做成可点击 Demo”写成“已验证需求”，将产物库改为左栏常驻，并把四态、全量语义参数、自动门禁等一并列为 P0，超出当前证据与 V13 设计范围。

原 v0.3 表述 修订结论
产物库常驻左栏，形成独立三栏设计应用 沿用 AutoClaw 左侧项目／任务和中间对话；当前任务结果在右侧打开产物工作区
draft/candidate/approved/superseded 四态均为已验证 P0 分开 Agent 执行状态、设计候选／工作版状态和交付确认；四态命名留待数据模型评审
选中即改为“零学习成本” V13 可点击样例能演示对象选择与确定值修改；真实用户理解度和 HTML 命中率未验证
生成后自动切画布，文件只是副产物 完成卡是入口；成果页先辨认 HTML 主稿、资源、参考和派生文件，再打开运行预览
无限画布一概不做 不做承载全部操作的无限画布；保留轻量手动画板组织和比较产物
Agent 多候选一概不向用户展示 方向探索阶段允许比较方案；局部修订候选必须供设计师审阅，不静默替换工作版
一次定稿自动通过全部交付门禁 机械检查与人工采用分离；真实 HTML 检查项、阈值和阻断级别待工程验证

2. 目标用户与核心任务

主要用户为产品设计师：已通过自然语言、PRD、截图或 Figma 参考发起 Design 任务，Agent 生成初版后，设计师需要找出可运行主稿、判断效果、改动具体对象，并把确定版本交给开发。产品经理与前端是 Task 2 的评审参与者，角色权限尚不属于 Task 1 MVP。

成功路径：任务完成 → 识别主稿与资料 → 运行预览 → 定域修改 → 候选对比 → 人工采纳 → 固定交付版本 → 导出文件和说明。没有用户任务测试，不能声称该流程已证明比现有方式更快。

3. 产品结构与数据对象

AutoClaw
├─ 项目 / 任务侧栏（沿用）
├─ 当前任务对话：输入、Agent 过程、结果卡（沿用并扩展）
└─ 右侧产物工作区
   ├─ 成果：主稿、资源、参考、派生文件、轻量画板
   ├─ 预览与编辑：页面 / 状态 / 设备 / 版本、对象与修改
   └─ 版本与交付：工作版、隔离候选、采纳记录、快照

DesignTask 关联对话和产物集；SourceBundle 保存 HTML 入口、CSS/JS 和依赖资源；Reference 保存 PRD、截图、Figma 链接及来源；DerivedAsset 记录来源版本；View 记录页面、状态、断点和版本；Candidate 记录基线、目标对象、影响文件和审阅结论；DeliverySnapshot 固定交付版本、文件清单、运行方式、检查结果和已知问题。主稿为可运行项目，截图和画板卡片不是其权威源。

状态分为三条独立信息，不用一个 done 统称：

  1. Agent 执行：运行中、已完成、失败。已完成只表示生成任务结束。
  2. 设计版本：当前工作版、待审候选、历史版本。采纳候选产生新工作版，不覆盖历史。
  3. 交付决定：未确认、已由用户确认的交付快照。Agent 可建议，但不代替设计师确认。

完整状态机、回滚分支及多人批准权在工程评审后定义。应保存可追溯记录，但不以“所有历史永不可删除”作为未经评估的产品规则。

4. Task 1 功能要求

ID 优先级 要求 可检查结果
T1-01 P0 完成结果卡提供“打开产物工作区”入口 不翻找聊天记录即可进入当前任务的成果页
T1-02 P0 成果页区分 HTML 主稿、运行资源、参考与派生物 每个对象可见角色、来源和对应操作；缺依赖时标注不可运行
T1-03 P0 选择页面／状态／设备／版本并运行预览 预览来源版本明确，切换后定位信息同步更新
T1-04 P0 点选对象并确认目标范围；确定值修改或 AI 局部候选 候选采纳前不改工作版，失败时可返回基线
T1-05 P0 对比候选与工作版，展示改动范围和待复核视图 设计师能采纳、放弃或继续调整候选
T1-06 P0 固定人工确认的交付快照并导出 预览、源文件、资源清单和说明指向同一版本
T1-07 P1 轻量画板组织参考、缩略图和方向卡 可摆放、分组、打开来源，不承担 HTML 源码编辑
T1-08 P1 语义 token 与跨视图影响检查 需要真实 HTML 项目和设计系统输入后定义验收

生成前的歧义追问是可选的约束澄清机制：只有关键要求存在多种解释、且不同解释会显著改变结果时才触发。不能把 Demo 中的追问时间或生成百分比当作真实性能数据。对象圈选也不应直接等同于可编辑组件；必须先确认命中的 DOM／组件范围。

5. Task 2 Feature：版本锚定的协作建议

受邀者的评论或修改建议绑定 version_id + view_id + target_ref。他们先看到固定版本的指定页面状态和对象，再提交建议；不能直接覆盖工作版。设计师选择把建议转为隔离候选，比较影响后采纳、拒绝或保留讨论。旧建议不随新版本自动迁移。Task 2 可以独立从已有版本开始，不重复 Task 1 的生成和交付全过程。

V13 原型仅本地模拟邀请、反馈和评审记录，未实现真实分享、权限、通知、并发或审计系统。这些能力不写入本轮已实现范围。

6. 验收与验证计划

已可在本地原型检查：SVG 示例中输入卡片圆角 25px→12px 的实际属性变化；隔离候选与工作版对比；人工采纳后保留历史；定稿下载的 SVG 与预览同源；SVG 尺寸、文字和位图元素的结构检查。测试 2 可检查建议的版本锚定展示和本地记录导出。这些仅是原型层验证。

进入工程前必须验证：真实 Design Agent 输出能否被识别为完整 HTML/CSS/JS 项目；点击或圈选区域能否稳定映射 DOM／组件；修改共享样式后是否影响其他页面或断点；预览与导出包是否可复现；依赖缺失或检查失败时是否能正确阻断交付。建议选择一份真实生成项目，连续做两次局部修改，并由前端在另一设备打开交付包复核。

进入产品判断前必须验证：设计师能否独立找到主稿、理解候选与工作版差别、识别“Agent 完成”与“人工确认”的区别；PM 和前端能否在固定版本给出可定位建议。记录成功率、错误位置、返工次数和主观困惑，不预设“零学习成本”或效率提升数字。

7. 本轮边界与待决问题

本轮不做完整无限画布、自由拖拽改布局、多人实时同编或从零建设设计系统。轻量画板与对象级修改仍保留。待决问题包括：HTML 对象身份如何跨版本保持稳定；圈选未解析到对象时如何降级；共享样式影响如何提示；交付快照采用复制还是不可变引用；设计 token 缺失时是否允许局部属性修改；Task 2 的真实角色与批准权如何定义。上述问题需要真实项目和参与者验证后再定优先级。
